# 0009. 확정 API 비동기 전환 — 202 접수, 판정은 예매에 남긴 결제 상태로 (3단계)
날짜: 2026-09-30 · 단계: 3 · 상태: 결정 · [English](0009-async-confirm-payment-status.en.md)
## 문맥
ADR 0008로 확정 요청이 `PaymentRequested`를 발행하게 되면서 확정 API는 PG를 부르지 않고 202로 "접수"만 한다. 판정은 결제 결과 쪽지가 돌아온 뒤에 난다. 그런데 거절은 상태 전이가 아니라(HELD 유지) 조회만으로는 "결제 중"과 "거절됨"이 똑같이 HELD로 보였고, 결과가 오기 전 새 접수번호로 한 번 더 확정하면 쪽지가 두 장 나가 돈이 두 번 승인됐다. 서버에는 결제 금액도 없었다(웹 상수뿐).
## 선택지
- **예매에 결제 진행 상태 칸** (채택): `payment_status`(REQUESTED·APPROVED·DECLINED·FAILED)와 `payment_tx_id`를 reservation에 둔다. 확정 요청과 결과 컨슈머가 각자 갱신한다.
- 예매 상태에 `PAYMENT_PENDING` 추가: 만료 조회·취소·웹의 HELD 분기가 연쇄로 바뀌고, 거절 표지는 여전히 따로 필요하다.
- payment 테이블을 조회에 붙인다: 모듈 경계를 넘는다. 체크리스트 11에서 payment를 떼어내면 서비스 간 동기 호출이 된다.
- 결과 전달: 예매 단위 SSE 대신 **조회 폴링**(채택). 좌석 SSE는 공개 스트림이라 예매를 식별하지 못하고 거절은 좌석 상태를 바꾸지 않는다.
## 결정
결제 진행 상태를 예매에 기록한다. 결제 중(REQUESTED)에는 새 확정·취소를 도메인이 `PAYMENT_IN_PROGRESS`(409)로 막고, 동시에 겹친 요청은 예매의 낙관적 락이 한쪽만 커밋시킨다 — 이중 결제 방어. 웹은 202를 받으면 판정이 날 때까지 같은 접수번호를 지키며 조회를 1초마다 폴링한다(상한 20초 뒤 "결제 결과 확인"). 실패(FAILED)는 되돌리기로 EXPIRED가 되지만 표지로 5분 만료와 구분한다. 금액은 서버 설정값(`ticket.price-krw`, 가격 모델이 생기기 전까지)으로 정한다 — 클라이언트 금액은 믿지 않는다.
## 결과
얻는 것: 결제가 느려도 확정 요청은 밀리초에 끝나고, 거절·실패·승인번호가 조회에 드러나 새 탭·다른 기기에서도 같은 판정을 본다. 잃는 것: 예매에 칸 두 개(V5), 판정까지 2~4초의 대기(릴레이 1초 × 두 번), E2E·CI가 Kafka를 요구한다. 결제 도중 홀드가 만료되면 승인이 와도 확정되지 않아 "돈은 나갔는데 좌석이 없는" 창이 남는다 — 결제 타임아웃 되돌리기(체크리스트 7)와 환불 보상(backlog)에서 다룬다.
