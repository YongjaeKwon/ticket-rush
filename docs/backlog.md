# backlog — 현재 단계 밖 아이디어

지금 만들지 않는다. 한 줄씩만 적는다. 단계가 올라가면 꺼내서 ADR로 판단한다.

| 아이디어 | 왜 | 언제 |
|---|---|---|
| 보안문자(캡차) — 좌석 홀드 직전 | 봇 방어 3겹째. 티켓팅 UX의 표준 단계 | 3단계 선택 |
| 다좌석 동시 홀드 (Redis Lua) | 1단계는 단일 좌석. 원자적 다좌석 홀드는 별도 학습 항목 | 2~3단계 |
| Outbox 릴레이 Debezium CDC 버전 | 폴링 방식과 비교해 ADR | 3단계 이후 |
| API Gateway (Spring Cloud Gateway) | 서비스 3개 이후에만 의미. 넣으면 ADR | 3단계 선택 |
| 가상 스레드 on/off 비교 | 홀드 API 처리량·p99 | 4단계 |
| 웹 푸시 (PWA) | 앱 푸시와 비교용. iOS 제약 확인 | 5단계 이후 |
| 예매 취소 → 환불 흐름 | 결제 되돌리기의 사용자 주도 버전 | 3단계 이후 |
| 관리자 화면 (공연·회차 등록) | 범위 밖. 시드 데이터로 대체 | 안 함 |
| 대기열 예상 대기시간 계산 | 입장량 N과 현재 순번으로 추정 | 2단계 |
| 실 PG 테스트모드 어댑터 (토스페이먼츠 등) | PaymentGateway 포트 구현체 교체 — 도메인 불변 증명. 웹훅·금액 검증 포함 | 3단계 이후 선택 |
| 같은 멱등 키의 동시 요청 방어 (서버 `SET NX` 선점 + 대기) | 지금은 마지막 응답이 저장 레코드를 덮는다. 최악의 경우에도 이중 확정은 안 되지만(confirmed_seat PK가 막는다) PG는 두 번 불릴 수 있다 | 4단계 부하 검증과 함께 |
| PG 승인 뒤 서버 오류 시 재승인 방지 (PG에 멱등 키 전달) | 3단계에서 확정은 비동기(ADR 0009)가 됐고 결제 중 재요청은 막히지만, payment 쪽 트랜잭션이 승인 뒤 실패해 재전달되면 PG를 다시 부른다(mock이라 실피해 없음) | 실 PG 어댑터와 함께 |
| 결제 거절 시뮬레이션 토글 (화면에서 PG 거절 유도) | 지금은 서버를 `--payment.mock.failure-rate=1.0`으로 띄워야 거절 UI를 본다 | 4단계 데모 모드 |
| 결제 시도 로그 패널 (키 앞 8자·재사용 여부·응답 코드·ms) | 멱등 재시도가 눈에 보이는 증거. README 수치 자리 | 4단계 데모 모드 |
| 결제 화면 이탈 시 홀드 취소 (`DELETE /reservations/{id}`) | 뒤로가기로 좌석맵에 가면 홀드가 남은 시간만큼 살아 있다. 지금은 활성 홀드를 복원해 "결제하기" 버튼을 되살리는 것으로 대신한다 | 2단계 이후 |
| React Compiler 린트 규칙(`react-hooks/set-state-in-effect`) 정리 | 데이터 로딩·타이머 효과가 규칙에 걸린다(기존 대기열·좌석맵 화면 포함). CI에 웹 린트를 붙일 때 한 번에 | 2단계 E2E 항목 |
| 1인 다좌석 홀드 차단 | 서버는 한 사용자의 홀드 수를 제한하지 않는다("1인 1매"는 문구뿐) | 3단계 |
| 승인 후 confirmed_seat 충돌 시 환불 보상(PaymentRefundRequested) | 돈은 승인됐는데 좌석은 남이 확정한 경우 — 지금은 로그만 남기고 장부에 기록해 재처리를 막는다. mock PG라 실피해 없음 | 실 PG 어댑터와 함께 |
| 홀드별 고유 토큰(비교-삭제 키 값) | 지금은 userId 비교라 같은 사용자가 같은 좌석을 연속 재선점하면 신구 홀드를 구분 못 한다(교차 사용자 피해는 막힘) | 4단계 부하 검증과 함께 |
