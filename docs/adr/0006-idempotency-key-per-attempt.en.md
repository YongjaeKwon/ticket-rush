# 0006. Idempotency key for confirm (payment) — one per payment attempt (stage 2)
Date: 2026-09-03 · Stage: 2 · Status: decided · [한국어](0006-idempotency-key-per-attempt.md)
## Context
Hold and confirm POSTs require an `Idempotency-Key`. The server (IdempotencyFilter) stores the first response for a given user + key for 24 hours and replays it verbatim — **it stores 4xx responses as well as 2xx, and only skips 5xx.** It also does not block concurrent requests that share a key. Since confirm moves money, "when do we reuse the key and when do we mint a new one" is the double-charge defence itself.
## Options
- **New key per request**: simple, but a retry after a lost response becomes a fresh request and may charge twice. The idempotency key stops meaning anything.
- **One fixed key per reservation**: a retry after an unknown result is safe. But a PG decline (402) is stored and replayed too, so a user's retry never reaches the PG — it just replays the decline.
- **One key per payment attempt** (chosen): the key lives exactly as long as "one attempt the server has not ruled on yet". Unknown result (network error, timeout, 5xx) → same key. Server gave a verdict (success, decline, state conflict) → discard, next attempt gets a new key.
## Decision
One key per attempt. Keep it in `sessionStorage` per reservation so it survives a reload, and delete it the moment the server gives a verdict (success, decline, any 4xx). A 5xx is not stored server-side, so the key stays. A leftover key therefore means exactly one thing: an attempt whose result we never saw. When the result is unknown we do **not** resend the same key immediately; we first poll the side-effect-free GET for a few seconds, because the earlier request may still be running on the server and the server does not block same-key requests that arrive concurrently. A 5xx goes through the same procedure — the server may have failed after the PG approved, so there is no automatic resend. The classification lives in a pure, React-free function (`apps/web/src/lib/confirm-policy.ts`) pinned by unit tests.
## Consequences
Gained: a retry after a dropped confirm never charges twice, and a retry after a decline really calls the PG again. Lost: the client owns the key lifecycle (one storage slot, six branches), the "result unknown" state lasts a few seconds, and after that the user has to tap once more. Server-side same-key concurrency defence (`SET NX` claim) and re-approval prevention after a post-approval server error are revisited with the stage-4 load tests and the stage-3 payment split respectively.
